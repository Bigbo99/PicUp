# 聊天框 @图片功能设计方案

日期：2026-09-15  
状态：待实施方案，本文件不代表功能已经开发或验证完成。

## 1. 目标

让用户在描述中直接引用图片，例如：

```text
以 [缩略图 主体.png] 作为主体，加入 [缩略图 人物.png] 中的人物。
```

界面里的图片引用、发送时的提示词、实际传给模型的图片必须一一对应。文件名只用于展示，绑定关系使用稳定的文件 ID，避免同名图片、调整顺序或重复引用造成错配。

## 2. 输入交互

支持点击上传、拖拽和粘贴添加图片；输入 `@` 或点击工具栏的 `@` 按钮打开图片选择列表。首版候选范围建议限定为当前草稿附件及当前会话中仍有访问权限的图片。

选择列表显示缩略图和文件名，支持搜索、上下键选择、Enter 确认和 Esc 关闭。选择后在光标处插入图片引用，光标移动到引用后方，用户可以继续输入描述。

图片引用采用不可拆分的行内节点：

- 显示缩略图和简短文件名，完整文件名通过悬浮提示展示。
- 点击可预览原图，删除时整体删除引用，不允许编辑内部文件 ID。
- 同一图片可以在描述中出现多次，不重复上传文件。
- 长文件名省略显示，引用节点随正文换行，兼容手机宽度。
- 支持撤销、重做、选区删除、复制粘贴和中文输入法。
- 中文输入法正在组词时，Enter 不触发发送或候选确认。

附件区和正文引用分别管理：删除一处引用不删除文件；删除最后一处引用后，如果图片仍在附件区，则继续作为普通附件发送。若同时不在附件区，也没有其他引用，则不再发送该图片。移除附件区图片时，仍被正文引用的图片继续保留发送资格，界面应体现这一状态。

## 3. 编辑器与数据结构

普通 textarea 无法直接渲染行内缩略图，建议使用成熟富文本编辑器的行内原子节点能力，例如 Tiptap 或 Lexical。实施时优先复用项目已有依赖，再确定选型。

编辑器内部保存文本节点和图片节点。发送时将节点序列化为提示词和引用表，避免从界面 HTML 反向猜测绑定关系。

```ts
type ImageRef = {
  refId: string;  // 当前消息内的引用键，如 img_1
  fileId: string; // 服务端图片文件 ID
};

type CreateJobRequest = {
  promptVersion?: 1;
  prompt: string;
  imageRefs?: ImageRef[];
  imageIds?: string[]; // 保留现有普通附件字段
};
```

文件名、缩略图和 MIME 类型属于展示元数据，可保存在草稿缓存中；后端必须根据 fileId 查询真实文件信息。不要把客户端传入的文件名、MIME 类型或 URL 当作可信依据。

首版采用占位符表示正文中的引用位置：

```json
{
  "promptVersion": 1,
  "prompt": "以 {{img:img_1}} 作为主体，加入 {{img:img_2}} 中的人物。",
  "imageRefs": [
    { "refId": "img_1", "fileId": "file_subject" },
    { "refId": "img_2", "fileId": "file_person" }
  ],
  "imageIds": []
}
```

绑定链路为 `占位符 -> refId -> fileId`。不额外保存 position 字符偏移量，避免正文编辑、中文和表情字符导致位置数据失效。

同一个 refId 可以在正文中出现多次，但引用表中只能定义一次。占位符是保留语法，编辑器对用户手动输入的同形文本进行转义；后端解析器须使用相同转义规则，且只在 promptVersion 为 1 时启用解析。普通字符串不能自动获得图片访问权限。

## 4. 服务端校验

发送前固定草稿快照，等待其中的图片上传完成，再生成请求。服务端依次完成以下检查：

1. 检查版本、字段结构、占位符语法及请求大小。
2. 检查每个占位符都存在对应的引用表条目。
3. 拒绝重复定义的 refId；允许正文重复使用同一个 refId。
4. 拒绝引用表中未被正文使用的条目，避免无效数据残留。
5. 检查所有引用文件和普通附件的访问权限、有效状态及真实图片类型。
6. 检查模型及供应商支持的图片数量、大小、格式和输入方式。
7. 根据最终将发送的图片集合构建请求。

最终图片集合为正文引用图片与普通附件的并集，按 fileId 去重。模型限制应同时考虑不同图片数量和实际发送的图片内容块数量。

建议错误码：

| 错误码 | 含义 |
| --- | --- |
| IMAGE_REF_NOT_FOUND | 正文引用缺少映射 |
| IMAGE_REF_DUPLICATE_DEFINITION | 引用表重复定义同一个 refId |
| IMAGE_REF_UNUSED | 引用表包含未使用条目 |
| IMAGE_FILE_NOT_AUTHORIZED | 当前用户无权访问图片 |
| IMAGE_NOT_READY | 图片上传或处理尚未完成 |
| IMAGE_UNAVAILABLE | 图片已删除或不可用 |
| IMAGE_LIMIT_EXCEEDED | 超出当前模型输入限制 |
| MODEL_DOES_NOT_SUPPORT_IMAGE | 当前模型不支持图片输入 |

## 5. 提示词构建与模型适配

新增独立的提示词构建模块，负责解析引用、确定图片顺序和生成内部消息表示。

```ts
type BuiltPrompt = {
  parts: Array<
    | { type: "text"; text: string }
    | { type: "image"; fileId: string; refId: string }
  >;
  referencedImageIds: string[];
};
```

上例可转换为：

```json
[
  { "type": "text", "text": "以 " },
  { "type": "image", "fileId": "file_subject", "refId": "img_1" },
  { "type": "text", "text": " 作为主体，加入 " },
  { "type": "image", "fileId": "file_person", "refId": "img_2" },
  { "type": "text", "text": " 中的人物。" }
]
```

以上是应用内部结构，不是任何供应商可直接接受的 API 请求。适配层必须根据实际接口转换成图片 URL、文件字节、Base64 或供应商自己的文件 ID。本地 fileId 不能直接当作供应商文件 ID。

对于支持图文交错输入的接口，按正文顺序转换消息片段。对于使用独立图片数组的图像编辑接口，按正文首次引用顺序编号，普通附件排在其后，重复文件仅传一次：

```text
提示词：以图片 1 作为主体，加入图片 2 中的人物。
图片数组：[主体图片, 人物图片]
```

同一图片再次被引用时继续使用同一编号。服务端应将编号直接替换到描述中，而非仅把原始占位符交给模型。

该协议可以保证传输层图片对应关系正确；模型能否准确执行“主体”“人物”等语义要求仍需使用真实模型验收，不能由编号机制保证。

## 6. 消息持久化与草稿恢复

在现有任务或消息记录上增加可选的 promptVersion 和 imageRefs，并保留原始 prompt。现有 inputFiles 记录本次实际使用的图片集合，具体字段落点实施时根据数据库结构确认。

- 历史消息使用原始 prompt 和引用表恢复行内图片展示。
- 旧消息没有版本和引用表时继续按原逻辑展示，不解析类似占位符的普通文本。
- 图片不可用时显示占位状态，保留原描述位置。
- 草稿同时保存编辑器内容及上传映射；临时预览 URL 不能作为持久地址。
- 发送失败保留草稿，重试使用同一份消息快照或明确重新生成快照。
- 日志记录引用键、文件 ID 和顺序即可；不要默认记录图片原始数据或带凭证的临时 URL。

## 7. 发送与异常状态

| 状态 | 行为 |
| --- | --- |
| 图片上传中 | 禁止发送，显示上传进度 |
| 上传失败 | 支持重试或移除失败图片 |
| 引用失效 | 标记对应节点，修复或删除后发送 |
| 模型不支持图片 | 显示原因并支持切换模型 |
| 图片数量超限 | 标明当前数量和限制 |
| 请求发送中 | 固定本次快照，防止重复提交 |
| 请求失败 | 保留输入和图片引用，支持重试 |

## 8. 兼容与实施顺序

旧请求继续使用 prompt + imageIds。新请求通过 promptVersion 明确启用引用解析，imageIds 和 imageRefs 共存时按并集处理，不能因采用新协议而静默丢弃普通附件。

建议实施顺序：

1. 确认当前模型接口能力，确定引用语法、转义规则及发送顺序。
2. 增加请求字段、服务端校验和提示词构建模块。
3. 接入编辑器图片节点、候选列表和上传流程。
4. 接入消息保存、历史展示及草稿恢复。
5. 完成异常处理及真实模型验收。

首版不加入自动识别主体、自动分配图片用途或跨会话全库搜索。图片在请求中的用途由用户的描述表达。

## 9. 验收清单

- [ ] 纯文本及旧版图片附件请求保持可用。
- [ ] 一张图片与文字混合输入能够正确发送。
- [ ] 两张同名图片分别绑定到正确文件。
- [ ] 两张图片交换引用顺序后，提示词和实际图片仍对应。
- [ ] 同一图片重复引用时允许发送，图片编号保持一致。
- [ ] 删除引用、移除附件、撤销操作后的最终图片集合正确。
- [ ] 上传未完成、失败、无权限和文件失效时有明确反馈。
- [ ] 用户手动输入占位符样式文本不会被误解析。
- [ ] 中文输入法、键盘选择、选区删除及复制粘贴正常。
- [ ] 桌面和手机上的引用节点不会撑破输入框。
- [ ] 刷新后草稿可恢复，历史消息可恢复原引用位置。
- [ ] 不同供应商的最终请求格式和图片顺序均经过验证。
- [ ] 使用内容明显不同的图片验证“主体”“人物”和对比描述，检查模型实际结果。

## 10. 补充技术讲解

前文已介绍过结构化消息、占位符绑定、Prompt Builder、DTO、多模态模型和消息快照，这里仅补充新增术语。

- **行内原子节点**：在正文中像一个完整字符一样移动和删除的组件，图片缩略图与文件 ID 不会被拆开编辑。
- **序列化**：把编辑器里的文本和图片节点转换成可以发送、保存的 JSON 数据。
- **适配层**：把项目统一的数据结构转换成不同模型接口要求的格式。
- **转义**：给有特殊含义的符号加上约定标记，让系统知道它只是普通文字。
- **去重**：同一张图片被引用多次时，合并重复的文件输入，避免无谓地重复传输。
